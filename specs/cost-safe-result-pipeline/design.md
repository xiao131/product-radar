# 设计

## 流水线

发现任务拆成两个可恢复阶段：

1. `COLLECTED`：批量调用 DataForSEO，信号去重入库，并立即写入当前任务的 `result_json`。
2. `COMPLETED`：从数据库读取尚未关联的自动证据，交给 AI 聚类和判断，生成候选产品。
3. `RESEARCH`：候选形成后创建独立 Standard 批量调研任务，采集多市场证据并生成正式评分。

如果第二阶段失败，任务状态为 `FAILED`，但 `result_json.collectionCompleted` 仍为 `true`。当天手工重试先查询该标记，直接复用数据库证据。

## 调度策略

- 备份与批量调研仍以“当天成功完成”为判断条件。
- 自动发现改为“当天是否尝试过”为判断条件。
- `RUNNING`、`COMPLETED`、`FAILED` 均视为已尝试，避免故障风暴。

## 预算策略

在现有 DataForSEO 总日/月预算之外增加发现专项日预算：

- 环境变量：`MAX_DATAFORSEO_DISCOVERY_COST_PER_DAY_USD`
- 默认值：`0.05`
- 适用范围：operation 以 `discovery_` 开头的所有预留费用
- 检查时点：真实 HTTP 请求之前

正常的一批发现任务预计约 0.036 美元，0.05 美元允许一次完整批次，但阻止同日第二批。

界面分别展示 usage ledger 行数（计费提交）、`units` 合计（计费子任务）和
DataForSEO 返回的实际美元费用，避免把一个包含多项任务的批量 POST 误解为多次请求。

## 去重策略

为 `signals` 增加：

- `canonical_key`：自动证据的稳定身份键
- `duplicate_count`：该证据累计合并的来源条数

身份键规则：

- App Store：App ID
- 搜索趋势/关键词：市场 + 规范化标题
- 网页、论坛、Reddit：市场 + 规范化标题

规范化包括 Unicode NFKC、转小写、去标点和合并空白。入库时优先匹配原始指纹，其次匹配身份键。历史自动信号在迁移后安全归并；若关联到了不同候选产品则保留。

## 产品界面

不改变现有技术栈和主要路由，只调整信息架构：

- 一级：今日结论、候选产品、我的产品
- 二级“数据与系统”：原始证据、运行状态

首页不再把“待处理信号数量”当作核心成果。原始证据页面明确告知系统会自动归并，自动证据不再提供逐条人工转候选操作。

AI 成功返回后，为本轮输入信号写入 `ai_reviewed_at`、`ai_review_count` 和
`last_ai_run_id`。后续批次优先选择审阅次数更少的证据。AI 返回的 0–1 小数
置信度会转换为 0–100 百分制，完整调研结果仍会覆盖该临时置信度。
