# Product Radar Hardening Requirements

## Goal

让产品雷达的推荐始终可证明为“当前结论”，让单候选动作严格限制在单候选范围，并补齐输入安全、可追溯性、任务反馈、可访问性和长期运行性能。

## User stories

1. 作为管理员，我只希望首页展示仍然有效的结论，过期判断必须明确标记。
2. 作为管理员，我在候选详情点击调研时，只希望处理当前候选并可持续看到任务状态。
3. 作为管理员，我希望区分“待调研”和“继续观察”，不把流程状态当成业务结论。
4. 作为管理员，我希望每份报告只展示它实际使用的证据，同时仍能查看最新证据与历史。
5. 作为管理员，我希望能安全导入 CSV、编辑产品和候选，并从任何操作获得明确反馈。
6. 作为键盘或移动端用户，我希望所有主流程控件可聚焦、可操作且状态可被辅助技术读取。

## Acceptance criteria

- 当产品、候选定义或关联证据发生变化时，系统应保留上次调研时间和历史报告，并将当前结论标记为失效。
- 当首页返回优先候选、涨分候选、观察列表或“现在开发”统计时，系统应只使用 `READY` 候选。
- 当候选不是 `READY` 时，界面应显示待调研、调研中或失败状态，不应把旧评分和旧 verdict 表达为当前结论。
- 当管理员在候选详情启动调研时，后台任务应只包含该候选；只有批量入口才能选择全部到期候选。
- 当研究任务返回 job ID 时，页面应跟踪该 job 直至完成或失败，并在完成后刷新数据。
- 当详情展示“本次判断的证据”时，系统应使用最新报告保存的 evidence snapshot；当前证据与历史报告应采用有界加载。
- 当管理员清空产品说明或当前重点时，PATCH 应保存空字符串而不是返回 500；只有可空 URL 可转换为 NULL。
- 当用户提交产品、信号、CSV 来源或 AI Base URL 时，系统应只接受无凭据的 HTTP/HTTPS URL。
- 当 CSV 包含标准引号、多行字段、所有合法 source type 或非法行时，系统应正确解析并返回准确行号错误，不得静默改写合法或非法来源。
- 当管理员使用候选筛选、排序和分页后打开详情并返回时，URL 应恢复原状态。
- 当管理员新增信号、编辑产品或编辑候选时，界面应提供可被辅助技术读取的成功或失败反馈。
- 当弹窗打开时，焦点应进入弹窗、被限制在弹窗内、背景不可交互；关闭后焦点应返回触发器。
- 当移动侧栏关闭时，侧栏应退出无障碍树和键盘顺序；打开和关闭时应正确转移焦点。
- 当键盘用户浏览候选表格时，应存在语义正确、可聚焦的详情链接或按钮。
- 当详情、任务和证据历史持续增长时，API 和 UI 应保持有界；页面隐藏时不应继续高频轮询。
- 当生产构建完成时，字体资源应只包含项目实际需要的子集，并保留当前视觉系统。

## Constraints

- 不删除历史报告、旧 verdict 或上次调研时间。
- 不改变真实数据预算、认证、CSRF 和密钥边界。
- 不引入新的前端框架或替换现有路由。
- 保留现有 Industrial / utilitarian 视觉语言。

## Non-goals

- 不重做产品评分算法。
- 不部署、不提交 Git、不调用真实付费数据源。
- 不进行品牌或整体信息架构重设计。
